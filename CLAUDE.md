# PegasLogistic v1 — правила разработки

Проект живёт на проде с реальными сотрудниками. Язык всего — русский
(код-комментарии, коммиты, интерфейс, общение).

## Логика обновления инструкций (обязательно)

Инструкции сотрудников — `public/assets/guide.js` (массив `GUIDES`).
Любое изменение поведения интерфейса или процессов сопровождается
**в том же коммите**:

1. правкой соответствующего раздела `GUIDES` — тексты должны совпадать
   с реальными кнопками и порядком действий;
2. установкой поля `updated: 'ГГГГ-ММ-ДД'` (сегодняшняя дата) в каждом
   изменённом разделе — по этой дате у сотрудников загорается точка на
   кнопке «?» и бейдж «обновлено» на вкладке раздела, пока они не
   откроют инструкции.

Изменение без правки гайда допустимо только если поведение для
сотрудников не изменилось (рефакторинг, исправление данных).

## Рабочий цикл задачи

задача → код → `node --test` (все зелёные) → правка гайда + `updated` →
коммит (русское сообщение, трейлер Co-Authored-By Claude) → push в main →
деплой: `ssh root@91.144.178.239 'cd /opt/pegas-planner && git pull
--ff-only && docker compose up -d --build'` → проверить `git log -1`
на VPS (DNS github.com там падает — pull может молча не пройти) и статус
контейнера «Up N seconds» (up --build иногда не перезапускает) →
прод-проверка в браузере → обновить память проекта.

## Концепция живых нормативов (зафиксирована 08.09.2026 — обязательна)

Система построена на самонастройке: «факт → норматив → решение → отчёт
о дрейфе». Руками задаются только ЦЕЛИ (настройки), всё остальное
система выучивает из фактов. КАЖДОЕ последующее изменение проверяется
на соответствие — конфликт с концепцией недопустим.

**Принципы:**

1. **Никаких новых зашитых бизнес-констант.** Любое пороговое число —
   либо из «Настройки» (цель, задаёт руководитель), либо выучено из
   факта (медиана с минимумом образцов), либо формула-фолбэк — и только
   на случай, когда факта ещё нет. Фолбэк пофрагментный: чего факт не
   знает, добирает формула, остальное — из факта.
2. **Ноль в настройке — осознанное значение.** Дефолт подставляется
   только вместо пустоты (урок 08.09: `|| дефолт` затирал нули
   калькуляции и раздувал переменные с 70 до 83,5 ₽/км).
3. **Выученное значение всегда в клампе.** Коридор здравого смысла
   защищает от вырожденных данных: коэффициент дорог 1,05–1,45, порог
   подгона 150–500 км, пороги сегментов 12–40/6–20 т₽. Кламп отверг —
   работает прежнее значение, и это видно в логе.
4. **Новый контур обязан подключаться к существующим, а не дублировать
   их.** Живые нормативы и их функции: `variableCostPerKm()` (переменные
   ₽/км из калькуляции), `customerSegment()` (A/B/C/D от медианы маржи
   парка), `smartTransitHoursFor()` (транзит: дорога `leg_fact_km` +
   ворота `gate_facts`), `plannedKmFor()` (км: медиана плеча → прямая ×
   калиброванный коэффициент), `dock_max_km` (порог подгона из принятых
   рекомендаций). Новое время/км/деньги считать ТОЛЬКО через них.
5. **Каждый контур отчитывается о дрейфе.** Пересчёт пишет лог;
   покрытие и сдвиги попадают в «📐 Нормативы недели» (пн 08:10) или
   «🎯 Подбор ТС» (пн 08:00); разовые миграции данных — с меткой в
   `app_meta`, идемпотентно.
6. **Автоматика рекомендует, человек решает.** Факты ставит человек или
   датчик (автозакрытие — только с датчиковым подтверждением); массовые
   действия — по явному выбору (галки брони недели); замены рекомендаций
   — с осмысленной причиной, причины улучшают правила.
7. **Эффект изменения меряется данными Пилота** до/после (зазоры
   стыковки, техскорость, ворота, доля машино-суток по сегментам).

**Чек-лист перед каждым коммитом с новым правилом/порогом:**
- в diff появилось числовое бизнес-значение? → перенести в настройку
  или вывести из факта с клампом и фолбэком;
- время/км/деньги считаются через функции из п.4, а не своей формулой?
- дрейф нового норматива виден в еженедельной сводке?
- грепом найдены ВСЕ потребители изменённого норматива (аудит ниже)?
- какой метрикой Пилота замеряем эффект?

## Аудит сквозных связей (после каждой крупной фичи)

Завершая существенное изменение, прогнать аудит потребителей — грепом
по изменённым функциям/полям/статусам — и убедиться, что обновлены ВСЕ
зависимые места, а не только точка изменения:

1. **Информационные плашки и сводки**: KPI-плашки вкладок, бейджи,
   легенды, дашборд — показывают ли новые данные/статусы.
2. **Отчёты руководителя**: «📆 Отчёт дня», утренний авто-отчёт 07:00,
   «Показатели сотрудников», «Отклонения», табель — считают ли по
   актуальной логике (лучше через общую функцию, не дублями).
3. **Карточки**: карточка ТС, карточка сотрудника, карточка рейса —
   отражают ли новое состояние (пример пробела: подмена была в сетке,
   но не в карточке ТС — 1321c1b).
4. **Соседние роли**: видит ли изменение та роль, которой оно нужно
   (уведомления чата, задания, права tablo/manager — только чтение).
5. **Инструкции**: разделы GUIDES дополнены, `updated` = сегодня.
6. **Регламенты-документы** (docx): если изменение меняет порядок
   работы роли — отметить в ответе пользователю, что регламент
   требует переиздания.

Найденные пробелы закрывать сразу же, в той же сессии.
