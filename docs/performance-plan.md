# Проект «Скорость как в TMS» (04.11.2026)

Заказ руководителя: планер нагружается всё больше, есть жалобы на
подвисания — проверить и спроектировать ускорение по-промышленному.

## Диагностика 04.11 (прод, замеры)

1. **Бутстрап 21,4 МБ.** Полный снимок данных весит 21 380 694 байта и
   собирается ~2 с. Клиентский тик раз в минуту сверяет rev и качает
   снимок заново, НО rev сбрасывается ЛЮБОЙ записью любого пользователя
   (POST/PATCH → bootstrapCache.at=0). В рабочее время записи идут
   постоянно → почти каждый тик каждого из ~15 клиентов тянет 21 МБ и
   парсит их. Это и есть «подвисания»: парсинг и перерисовка 21 МБ на
   офисном ПК занимает секунды, экран замирает.
2. **CPU 33% в простое, RAM 334/512 МБ** (у потолка лимита контейнера).
   В октябре после «бустрап-диеты» было 2% — нагрузка вернулась:
   66 фоновых сторожей (минутные опросы Пилота, АТС, бота водителей;
   8 пятиминутных) + тики клиентов.
3. **Один поток на всех.** Node + синхронный SQLite: тяжёлый запрос
   (отчёт руководителя, PDF-колода, сверка) блокирует ВСЕХ пользователей
   на время выполнения.
4. **Мелкое:** у messages (124 659 строк) нет ни одного индекса —
   запросы по created_at в отчётах сканируют всё (~96 мс); audit_log
   95 589 строк и растёт без чистки; сжатие /api на пути nginx —
   проверить (в лоб ответ не сжат).
5. Лента чата устроена правильно (инкремент по id) — чат не виновник.

## Принципы (как в больших TMS)

- **Сначала измеримость, потом оптимизация.** Каждое «тормозит»
  превращается в цифру; каждое улучшение доказывается до/после
  (правило проекта «мерить эффект»).
- **Скорость — живой норматив**: p95 времени ответа по эндпоинтам и
  вес трафика считаются постоянно, дрейф виден в «📐 Нормативы недели»;
  деградация ловится ДО жалоб.
- **Инкрементальность**: клиент получает только изменившееся, полный
  снимок — исключение, а не норма.
- **Изоляция тяжёлого**: отчёты и внешние опросы не мешают оперативной
  работе смены.

## Этапы

### Э0 — Измеримость (фундамент, делается первым)
- Серверные тайминги каждого API-запроса: счётчик, p50/p95/max, вес
  ответа; копятся в памяти, срез пишется в app_meta; медленные
  (> порога из настроек) — в лог с путём и длительностью.
- Отдача «⚙ Скорость» в самонастройке: топ медленных эндпоинтов, динамика
  недели, объём отданного трафика по эндпоинтам.
- Клиентский маячок: время тика (скачивание + парсинг + перерисовка) и
  долгие задачи — батчем раз в несколько минут на сервер; видно, у кого
  из пользователей и на какой вкладке виснет.

### Э1 — Диета тика (главный эффект для пользователей)
- **Rev по разделам**: снимок делится на блоки (справочники: зоны,
  адреса, парк, водители ≈ редкие; оперативные: рейсы, заявки,
  назначения; лента: сообщения) — у каждого свой rev; тик забирает
  только изменённые блоки.
- **Окно данных**: в бутстрап не едут рейсы/заявки старше рабочего
  окна (история — отдельным запросом по требованию, как уже сделано
  в отчётах).
- Ожидание: типовой тик 21 МБ → десятки–сотни КБ; вход — одна полная
  загрузка, дальше инкременты.

### Э2 — Изоляция тяжёлого
- Тяжёлые сборки (PDF-колода, сверки, большие отчёты) — в worker_thread
  со своим read-only подключением к базе: event loop смены не блокируется.
- Кэши тяжёлых расчётов с честным временем жизни (сегменты уже так).

### Э3 — Ревизия сторожей
- Единый планировщик фоновых задач с разносом по времени (не толпиться
  на «ровной» минуте) и бюджетом длительности; журнал «кто сколько ел».
- Минутные опросы внешних систем (Пилот, АТС, бот) — кандидаты в
  отдельный воркер: сетевые ожидания и разбор телеметрии не должны жить
  в потоке HTTP.

### Э4 — База
- Индексы по горячим запросам (по данным Э0), ANALYZE по расписанию.
- Политика хранения: messages/audit_log старше N месяцев — в архивные
  таблицы/чистка (N — настройка руководителя); VACUUM в тихие часы.

### Э5 — Фронт
- Перерисовка только изменённых блоков при тике (renderInto уже бережёт
  ввод — расширить до точечных обновлений).
- Виртуализация длинных списков (гант, доска на сотни карточек).

### Э6 — Инфраструктура
- Поднять лимит памяти контейнера (334/512 уже впритык) — по ресурсам
  VPS; проверить сжатие /api на nginx (21 МБ JSON жмётся в разы);
  keep-alive до апстрима.

## Порядок и мерило

Э0 → Э1 (они дают основной эффект и доказательную базу) → Э2/Э3 →
Э4–Э6 по данным Э0. После каждого этапа — до/после по метрикам Э0 в
«📐 Нормативы недели».
